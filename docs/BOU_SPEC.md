# ぼぅ Instagram投稿システム 設計書（第一段階）

「がんばってなさそうに見えて、今日もちゃんと生きてる。」
マンボウの子・ぼぅのInstagram投稿を継続的に生成するための専用システム。

第一段階のゴールは **自動投稿ではなく**、
「テーマ生成 → 投稿文生成 → 画像生成用プロンプト生成 → 人が確認」
のサイクルを安定して回せること。

---

## 1. 推奨アーキテクチャ

このリポジトリは GitHub Pages で配信される **静的サイト（ビルドなし・バニラJS）** で統一されているため、
ぼぅのシステムも同じ流儀に合わせる。サーバー・DB・ビルド工程は持たない。

```
bou.html（管理画面・1ページ）
 ├─ styles/bou.css
 └─ scripts/bou/
     ├─ character.js   … ぼぅの固定設定（人格・話し方・NG表現・見た目・プロンプト雛形）
     ├─ store.js       … 保存層（localStorage。投稿候補・フィードバック・設定の永続化、書き出し/読み込み）
     ├─ generator.js   … 生成層（3案生成・NGワード検査・フィードバック学習の反映）
     └─ app.js         … 画面の配線（ダッシュボード／投稿詳細／キャラクター設定）
```

### 生成エンジンは2モード

| モード | 仕組み | APIキー | 用途 |
|---|---|---|---|
| 内蔵モード | ぼぅの声で書き溜めたコーパスから組み合わせ生成 | 不要 | すぐ試す・オフライン・下書きのたたき台 |
| Claude APIモード | ブラウザから Claude API（`claude-opus-5`）を直接呼ぶ | 必要 | 本番品質の3案生成。固定設定+過去フィードバックをプロンプトに注入 |

- APIキーは **ブラウザのlocalStorageにのみ** 保存され、リポジトリやサーバーには送られない
  （個人運用の管理画面である前提。共有PCでは使わないこと）。
- どちらのモードの出力も、保存前に **NG表現チェッカー**（「頑張って」「努力」「ポジティブに」等）を通す。

### なぜサーバーを立てないか
- リポジトリの既存アプリ（shrine / muubeat / dasazaurus …）がすべて静的+localStorageで動いており、運用が1本化できる。
- 第一段階は「人が確認して選ぶ」工程が主役で、常時稼働のバックエンドが不要。
- 第二段階（画像生成API・自動投稿）は、既存の `social/x-autopost.js` と同じく **GitHub Actions** に載せられる構造にしておく（後述）。

## 2. データ構造

すべて localStorage（キー接頭辞 `bou.`）。JSONエクスポート/インポートでバックアップできる。

### 投稿候補（`bou.posts` : Post[]）

```json
{
  "id": "p20260827-a1b2c3",
  "created_at": "2026-08-27T09:00:00.000Z",
  "updated_at": "2026-08-27T09:05:00.000Z",
  "batch_id": "b20260827-x9y8",
  "variant": "A",
  "theme": "返信",
  "main_text": "返信しようとは、思ってる。",
  "scene": "ソファでスマホを見ている",
  "image_prompt": "A soft hand-drawn watercolor illustration of ...",
  "pages": [
    { "text": "返信しようとは、\n思ってる。", "scene": "ソファでスマホを見る", "image_prompt": "... image 1 of 4 ..." },
    { "text": "文面も、\n半分できてる。", "scene": "打ちかけで止まっている", "image_prompt": "... image 2 of 4 ..." },
    { "text": "あとは、送るだけ。", "scene": "送信ボタンの前で固まる", "image_prompt": "... image 3 of 4 ..." },
    { "text": "…明日、送る。", "scene": "スマホを置いて寝る", "image_prompt": "... image 4 of 4 ..." }
  ],
  "caption": "気持ちは、もう届いてると思う。たぶん。",
  "hashtags": ["#ぼぅ", "#マンボウ", "#ゆるいイラスト", "#おつかれさま", "#今日はここまで"],
  "status": "draft",
  "generator": "api",
  "user_feedback": [
    { "at": "2026-08-27T09:10:00.000Z", "text": "これはぼぅっぽい" }
  ]
}
```

- 1投稿は **3〜5枚のカルーセル**。`pages[]` に各ページの文（1〜2行）・シーン・画像生成プロンプトを持つ。
  1枚目=共感の入り口（表紙）、中間=小さな展開、最後=力の抜けるゆるい着地。
  `main_text` / `scene` / `image_prompt` は1枚目（表紙）の複製（一覧表示と旧データ互換のため）。
- 各ページの画像プロンプトには「連作で同じデザイン・画風を保つ」指示（image N of M）が自動で付く。
- `status` : `draft`（生成直後）→ `selected`（採用）→ `generated`（画像作成済み）→ `posted`（投稿済み）。不採用は `rejected`。
- `batch_id` / `variant`（A/B/C）で「同じ日の3案」をひとまとめに管理。
- 1案を選ぶと、同じバッチの残り2案は自動で `rejected` になる（あとから戻せる）。

### フィードバック（学習用ログ）

- 各投稿の `user_feedback[]` に追記型で保存（「ぼぅっぽい」「言いすぎ」「もっとゆるく」等）。
- 生成時には次の3種類を参照する：
  1. **良い例** … `selected` / `generated` / `posted` の投稿（最近5件）
  2. **悪い例** … フィードバック付きで `rejected` された投稿（最近5件）
  3. **最近の言葉のフィードバック** … 直近10件のコメント
- Claude APIモードではこれをプロンプトに注入。内蔵モードでは「もっとゆるく」「言いすぎ」系の
  フィードバックが多いとき、より短い文を優先するなどの簡易調整を行う。

### キャラクター設定（`bou.character`）

`scripts/bou/character.js` の既定値をベースに、管理画面から編集した内容を localStorage に上書き保存。
「初期設定に戻す」でいつでも既定値へ。生成は **毎回このオブジェクトを参照** する。

主なフィールド：`concept` / `personality[]` / `speech`（話し方ルール・口ぐせ例）/
`ngWords[]`（絶対に使わない表現）/ `themes[]`（投稿テーマ一覧）/
`visual`（色コード・造形の固定設定・禁止事項）/ `imagePromptTemplate`（`{scene}` 差し込み式）/
`hashtagPool[]`。

## 3. 画面構成（bou.html 内の3画面）

### ダッシュボード
- **「今日のぼぅ投稿を作って」ボタン** → A案/B案/C案 の3案を生成（テーマ・文章・シーンを変えて）
- 今日の3案カード（メインテキスト・テーマ・シーン・「この案にする」ボタン）
- 過去投稿一覧（ステータスでフィルタ：下書き/採用/画像作成済み/投稿済み/不採用）
- データの書き出し/読み込み

### 投稿詳細（カードをタップで開く）
- テーマ / メインテキスト / シーン / キャプション / ハッシュタグ / 画像生成用プロンプト（コピー用）
- すべて修正欄として編集可能
- ステータス変更（採用 → 画像作成済み → 投稿済み / 不採用）
- フィードバック欄＋ワンタップチップ（「ぼぅっぽい」「これは違う」「もっとゆるく」「言いすぎ」「好き」）

### キャラクター設定
- ぼぅの固定設定（人格・話し方・NG表現・見た目・プロンプト雛形・ハッシュタグ候補）を閲覧・編集
- Claude APIモードの設定（APIキー・モード切り替え）
- NG表現に引っかかった生成物の扱い（警告表示）の説明

## 4. 第一段階と第二段階の切り分け

| | 第一段階（今回実装） | 第二段階（今後） |
|---|---|---|
| テーマ・投稿文・シーン生成 | ✅ 3案生成 | 同左 |
| 画像生成用プロンプト | ✅ 生成（人がコピーして画像ツールで使う） | 画像生成APIへ自動送信 |
| 画像そのもの | ❌（人が手動生成 → 「画像作成済み」に更新） | ✅ API生成・候補画像の保存 |
| Instagram投稿 | ❌（人が手動投稿 → 「投稿済み」に更新） | ✅ Graph API等での予約/自動投稿 |
| 保存 | localStorage + JSONエクスポート | リポジトリ内JSON（`social/bou-posts.json`）+ GitHub Actions |

第一段階の完成条件（すべて本実装で満たす）：
1. 「今日のぼぅ投稿を作って」で3案生成できる
2. 1案を選べる
3. 画像生成プロンプトが生成される
4. キャプションとハッシュタグが生成される
5. 過去の投稿候補を保存できる
6. ユーザーフィードバックを記録できる
7. ぼぅの固定設定を毎回参照する

## 5. 今後の画像生成API接続方法（第二段階）

接続しやすいように、生成層に **アダプタの差し込み口** を用意してある。

```js
// scripts/bou/generator.js
// 第二段階では、この関数を実装した画像生成アダプタを登録する。
// post.image_prompt（固定設定込みの完成プロンプト）を受け取り、画像URL/データを返す。
BouGenerator.registerImageAdapter({
    name: 'gemini-image',        // 例
    generate: async function (post) { /* fetch(...) */ return { imageUrl: '...' }; }
});
```

- 管理画面の「画像を生成」ボタンは、アダプタ未登録のときは「プロンプトをコピー」だけを表示。
  アダプタが登録されると自動でAPI生成ボタンが現れる設計（`app.js` は登録有無だけを見る）。
- `image_prompt` は第一段階から**そのままAPIに渡せる完成形**（英語・固定デザイン・禁止事項込み）で保存している。
- 候補API：Gemini（Imagen）/ OpenAI Images / Stability など。いずれも「プロンプト文字列 → 画像」の
  形なのでアダプタ1関数で吸収できる。
- ブラウザから直接呼べないAPI（キー秘匿が必要な場合）は、`social/x-autopost.js` と同じ方式で
  GitHub Actions + リポジトリSecretsに載せ替える。その際も Post のデータ構造はそのまま使う。

## 6. リサーチ・投稿戦略機能（追加要件の設計）

目的は模倣ではなく、Instagramで「なぜ見られる・保存される・フォローされるか」の**構造だけ**を抽出し、
ぼぅの世界観（急がない・解決しない・励まさない）に変換して使うこと。
最終目的は投稿量産ではなく、**キャラクターの一貫性とファン化**。

### 実装の切り分け（実装前の整理）

| 分類 | 内容 |
|---|---|
| **今すぐ追加できる機能** | 参考アカウントDB（シード33件＋手動追加編集）／人気パターン分析・ぼぅ変換ルールの閲覧／A・B・C型の3案生成／10項目の内部評価と自動再生成／使いすぎ検出（テーマ・シーン・語尾）／リサーチ・投稿戦略ページ／Phase別戦略／定期リサーチの手動記録 |
| **外部APIや検索が必要な機能** | Instagramの実データ取得（フォロワー数・保存数等）。Instagram Graph APIは自分のプロアカウント分析のみ可・他者アカウントの自動収集は規約上不可のため、**設計上も自動化しない** |
| **手動運用で代替する機能** | 月1回のリサーチ（本人がInstagramを見て、リサーチページの表とログに記入）／フォロワー数に応じたPhaseの切替／伸びた投稿の傾向メモ |
| **データに追加した項目** | 投稿: `proposal_type`（王道共感/本質/保存・シェア）・`evaluation`（10項目スコア・フラグ）。新規キー: `bou.research`（アカウント表・分析・変換ルール）・`bou.strategy`（Phase・方針8項目）・`bou.researchLog`（定期リサーチの追記ログ）。すべて書き出し/読み込みに含まれる |
| **管理画面に追加したページ** | 「リサーチ」（アカウント一覧・パターン分析・変換ルール・定期記録）／「投稿戦略」（Phase・戦略8項目・採用/不採用実績・使いすぎ警告） |
| **既存を壊さない実装順** | ①シードデータ（新規ファイル）→②store拡張（新キーのみ）→③generator拡張（評価・型は追加フィールド）→④新タブUI（既存タブは無変更）→⑤テスト。旧データは `proposal_type`/`evaluation` なしでもそのまま動く |

### リサーチデータの出所管理

- 各アカウントに `source_url` / `source_name` / `checked_at` / `verified` / `data_type` を保持。
  `data_type` は **verified**（外部情報源で実在とフォロワー数を確認済み）／**estimated**（観察メモ・数値未確認）／
  **manual**（管理画面から手動入力）／**placeholder**（要調査枠）の4区分。
- 初期データは Web検索経由でInstagramプロフィール等を確認し、**20件を verified 化**（2026-08-29時点。
  例: ちいかわ77.8万・ぐでたま82.6万・yumekanau2 66.8万）。未確認の13件は数値を「未確認」とし、
  参考レンジは `followers_est` に分離。**推定値を事実として保存しない**。
- 管理画面では全行にデータ種別バッジ（確認済み/未確認・推定/手動入力/要調査枠）を表示し、
  「確認済み」への変更には出所URLと確認日を必須にしている。
- 生成プロンプトには特定アカウントのデータは渡さず、一般的な構造分析のみを
  「未確認の推定を含む観察メモ・強い根拠にしない」と明示して渡す。

### 3案の型と評価

- **A案=王道共感型**（最も多くの人が「これ私」）／**B案=本質型**（静かにじわっと残る）／**C案=保存・シェア型**（短く、誰かに送りたくなる）
- 生成時に毎回参照: 採用/不採用の履歴・フィードバック・直近30件のテーマ/シーン/語尾の偏り・リサーチ分析・現在のPhaseと今週の方針
- 各案は10項目（ぼぅらしさ/共感度/新鮮さ/保存/シェア/フォロー期待/差別化/既視感/言いすぎ/世界観）で内部評価。
  説教・ポジティブ押しつけ・自己啓発表現・長すぎ・元気すぎ・既視感・テーマ/小物の連続は自動で弾いて選び直す
  （内蔵モード: 別候補を再選定／APIモード: 理由を添えて1回作り直し）
