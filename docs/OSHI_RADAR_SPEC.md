# 推し活レーダーOS 設計ドキュメント

「行けたはずの推しイベントを後から知る件数をゼロにする」ための個人用OS。
本ドキュメントは STEP1〜7 の設計と、現環境で実現可能な範囲の整理をまとめる。

---

## 前提：現在の環境で実現可能な範囲

このリポジトリは **GitHub Pages の静的サイト**（Vanilla HTML/JS/CSS）である。

| 項目 | 現状 | 影響 |
|---|---|---|
| バックエンドサーバー | なし | サーバーサイドDB・常駐クローラーは持てない |
| データベース | なし | Phase 1 は localStorage（端末内保存）で代替 |
| 定期実行 | GitHub Actions cron の前例あり（x-autopost） | Phase 2 の自動収集はここに載せられる |
| 外部API | GAS 連携の前例あり | Phase 3 のマルチユーザーDBは GAS+スプレッドシート or 外部BaaS |
| プッシュ通知 | 不可（Web Push はサーバー鍵が必要） | Phase 1 は「アプリを開いた時の朝チェック表示」で代替 |
| 地図・経路API | キーなし | エリア間移動時間は内蔵マトリクス（手入力補正可）で代替 |

### 技術的・規約上できないこと（明示）

- **X (Twitter) の検索取得**: 無料APIでは検索不可（投稿のみ）。スクレイピングは規約違反。→ SNS自動監視は不可。
- **Instagram 取得**: Graph API は自アカウントのみ。他者投稿の自動取得は不可。
- **一般Webスクレイピング**: 各サイトの robots.txt / 利用規約に依存。タワレコ・百貨店等の商用サイトは多くが自動取得を禁止。→ Phase 2 では「公式RSS / 構造化データがあるソースのみ」+「AI検索による下調べ→人が確認して登録」のハイブリッドが現実的。
- **ブラウザからの外部サイト fetch**: CORS で大半がブロックされる。クロールはブラウザではなく GitHub Actions 側で行う必要がある。

### 外部API・有料サービスが必要になる場合の候補（実装前提示）

| サービス | 用途 | 概算 | 無料枠 | 代替案 |
|---|---|---|---|---|
| Google Maps Routes API | 正確な移動時間 | $5/1000リクエスト〜 | 月$200クレジット | 内蔵エリアマトリクス（採用） |
| Brave Search API / Tavily | イベント自動検索 | $5〜/月 | あり（少量） | Claude/手動での定期検索→手動登録（Phase1採用） |
| Supabase / Firebase | マルチユーザーDB | 無料枠→$25/月 | あり | GAS + スプレッドシート（前例あり） |
| Web Push (VAPID) | プッシュ通知 | 無料（要サーバー） | - | GitHub Actions cron + メール/X DM、またはアプリ起動時表示（Phase1採用） |

## STEP1: システム全体設計

```
┌─────────────────────────────────────────────┐
│  oshi-radar.html（スマホPWA / GitHub Pages）  │
│                                             │
│  ┌─────────┐ ┌──────────┐ ┌─────────────┐  │
│  │ ホーム    │ │ イベント   │ │ 推し / 予定  │  │
│  │ ダッシュ  │ │ 一覧/登録  │ │ 登録/管理    │  │
│  └────┬────┘ └────┬─────┘ └──────┬──────┘  │
│       └───────────┼──────────────┘         │
│              ┌────▼─────┐                   │
│              │ logic.js │ スコアリング        │
│              │          │ 行けるか判定エンジン │
│              │          │ エリア移動マトリクス │
│              └────┬─────┘                   │
│              ┌────▼─────┐                   │
│              │ store.js │ localStorage      │
│              │          │ (JSON エクスポート/ │
│              │          │  インポートで移行可) │
│              └──────────┘                   │
└─────────────────────────────────────────────┘

Phase 2（将来）: GitHub Actions cron → 許可されたソースを取得
                → data/events.json をコミット → アプリが起動時にマージ
Phase 3（将来）: store.js の後ろを GAS/Supabase に差し替え（storeのAPIは維持）
```

- 中心は「情報を集めること」ではなく **「この日この場所にいるなら行ける」と判定すること**。
- store.js の読み書きインターフェースを固定し、将来バックエンドに差し替え可能にする。

## STEP2: MVPに必要なDB設計

localStorage キー `oshiRadar.v1` に単一JSONで保存。将来のマルチユーザー化を見据えテーブル相当を分離。

```
settings        … homeArea, searchRangeMin(10/30/60), notifyThresholds
oshi            … id, name, group, category, priority(1最推し/2高/3通常),
                  keywords[], excludeKeywords[], notify, createdAt
events          … event_id, name, organizer, category, oshiLinks[{oshiId, matchType}],
                  prefecture, city, venue, area(マトリクス参照キー),
                  startDate, endDate, openTime, closeTime, lastEntry,
                  fee, needsReservation, needsNumberedTicket, sameDayTicket,
                  freeEntry, freeEntryFrom, officialUrl, status, notes,
                  createdAt, updatedAt, lastVerifiedAt
event_sources   … eventId, url, name, official(bool), fetchedAt, verifiedAt
                  → 公式ソースが1つもない場合 UI で【要確認】表示
user_schedules  … id, date, items[{time, endTime, title, area}]
event_scores    … 保存せず毎回計算（元データが変わるため）。式は STEP5
notifications   … Phase 1 は「見逃し注意」欄として画面表示（保存不要）
locations       … travel.js 内エリアマトリクス（大阪/東京/三重 + ユーザー補正）
```

**一意性（誤認防止・要件18）**: `イベント名 × 会場 × 開始日 × 主催者` で重複チェック。
同名・同ブランドでも会場か主催者が違えば別イベントとして登録される。

## STEP3: 画面一覧

1. **ホーム（今日の推し活ダッシュボード）** — 🔥今から行けます / 今日開催中 / 見逃し注意(80点+) / 終了間近(7日以内) / 遠征予定と一致 / 新着(24h)。カード形式。
2. **イベント** — 一覧（スコア順）/ 追加・編集フォーム / 情報源管理 /【要確認】バッジ
3. **推し** — 登録・編集（関連キーワード・表記揺れ・除外語・優先度・通知ON/OFF）
4. **予定** — 日付ごとの外出予定（時刻・場所・エリア）登録 → 保存時に自動でその日の行動範囲のイベントを判定
5. **設定** — 拠点エリア / 検索範囲(徒歩10分・30分・60分) / データのエクスポート・インポート

管理画面（要件23）は Phase 1 では「イベント編集画面＝管理画面」を兼ねる（自分専用のため）。

## STEP4: 情報取得方法

- **Phase 1（現在）**: 手動登録。ただし登録フォームは「情報源URL・公式/非公式・取得日時・最終確認日時」を必須構造で持ち、後の自動化と互換。Claude への定期依頼（「今週の King & Prince イベントを調べて」）→ 結果を登録、が現実的な運用。
- **Phase 2**: GitHub Actions cron（毎朝）で、規約上取得可能なソース（公式RSS・構造化データ）を取得し `data/events.json` に反映 → アプリ起動時マージ。取得不可のソースは「確認先リンク集」として提示し人間が確認。
- **SNS 自動監視は上記の通り不可**（規約）。代替として公式サイトの更新検知を優先。

## STEP5: スコアリングロジック（100点）

```
推し一致度(最大40): 本人40 / グループ35 / コラボ30 / 関連作品20
  → イベントに紐付けた推しの matchType の最大値
日程一致(最大25): 今日開催中25 / 明日22 / 3日以内18 / 7日以内12 / それ以降5
距離(最大20): 徒歩圏(〜10分)20 / 15分以内18 / 30分以内15 / 60分以内8 / それ以上2
  → 基準点は「今日の予定エリア > 現在地(設定拠点)」の順で採用
緊急度(最大15): 今日終了15 / 3日以内12 / 7日以内8 / それ以上3
```

通知レベル: 90+ 🔥絶対チェック / 80-89 🔥見逃し注意 / 60-79 ⭐おすすめ / 40-59 💡近くなら / 39以下 通常

見逃し防止ブースト（要件17）: 条件A〜D該当時は「🔥今から行けます」枠へ昇格表示。

## STEP6: 「今から行ける」判定ロジック

入力: 現在時刻・現在エリア（今日の予定 or 拠点）・次の予定・イベント（開催時間/最終入場/フリー入場開始/整理券/推奨滞在20〜30分）

```
出発 = 今
到着 = 今 + 移動時間(現在エリア→会場エリア)
入場可能時刻 = max(到着, フリー入場開始 or 開場)
× 判定: 入場可能時刻 > 最終入場 or 閉場-15分
退店 = 入場可能時刻 + 推奨滞在(既定30分)
次予定到着 = 退店 + 移動時間(会場→次予定エリア)
余裕 = 次予定開始 - 次予定到着
  ◎ 余裕30分以上 / ○ 10分以上 / △ 0分以上(または滞在15分に短縮で間に合う) / × 間に合わない
予約必須でフリー入場なし → 判定に関わらず「事前予約制・要確認」を明示
```

出力はタイムライン（16:00出発 → 16:20到着 → 16:50退店 → 17:10 次予定）まで提示する。

## STEP7: 実装順序

1. store.js（データ層 + シード） → 2. travel.js（エリアマトリクス） → 3. logic.js（スコア + 判定）
→ 4. 画面（推し登録 → イベント登録 → 予定登録 → ホーム） → 5. 「今から行ける？」ボタン
→ 6. エクスポート/インポート → 7.（Phase 2）Actions cron 収集 → 8.（Phase 3）store 差し替え

## 絶対に守ること

- イベントは `名前×会場×開始日×主催者` で一意。似た名前でも別管理（要件18）。
- 公式ソースゼロのイベントは常に【要確認】表示。「開催中」と断定しない（要件5）。
- KPI は PV ではなく「後から知って悔しい件数 = 0」（要件25）。
