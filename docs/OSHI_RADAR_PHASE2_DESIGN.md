# 推し活レーダーOS Phase 2 情報収集エンジン設計

目的: **「手動登録しない限りOSがイベントを知らない」状態をなくす。**
KPIは「イベント管理の便利さ」ではなく「知らなかった推しイベントの発見」。

> 本書は設計のみ。実装はユーザー承認後に開始する。
> 印: ✅=この設計時にWeb検索で実在確認済み ／ ⚠️=実装時に要検証（本開発環境は外部サイトへの直接アクセスが遮断されており robots.txt 等を確認できなかった）

---

## 0. 結論サマリ

- **推奨アーキテクチャ: Cloudflare Workers + D1**（案2）。収集・DB・API・通知を1箇所で担え、無料枠で足りる。GitHub Pagesは当面フロント配信のまま併存可。
- 収集は2層構造:
  - **確定層（公式巡回）**: 決め打ちの公式ページを定期取得し、差分があればイベント抽出
  - **発見層（検索）**: 検索APIで「推しキーワード×イベント語」を回し、未知のイベント候補を拾う
- 発見したものは全て `discovered`（要確認）で入り、**公式ソースで裏取りできたものだけ `verified`** に昇格。「開催中」と断定表示するのは verified のみ。
- event identity は収集段階から `正規化イベント名 × 会場ID × 開始日 × 正規化主催者` で照合。自動マージは完全一致のみ、類似は「重複候補」として人間/AIレビューに回す。

## 2. 規約上問題なく取得できる情報（Q2）

- **事実データ（イベント名・日時・会場・料金・入場方法）は著作権の保護対象外**。保存・自分用利用は著作権上は問題になりにくい。紹介文の全文コピーはNG（保存するのは構造化した事実＋出典URLのみ）。
- ただし各サイトの**利用規約とrobots.txt**が別途制約になる。商業ECサイト（タワレコ・HMV等）は「自動アクセス禁止」条項を持つことがある。対応方針:
  1. **robots.txt を実装時に全ドメイン分確認**し、Disallow のパスは取得しない（fetcherに robots.txt チェックを組み込み、結果を7日キャッシュ）
  2. アクセスは **1ソースにつき1日1〜3回・1接続・タイムアウト付き**（人間がブラウザで見るより遥かに少ない負荷）
  3. User-Agent に連絡先を明示
  4. 取得するのは**一覧/ニュースページのみ**。全ページクロールはしない
  5. **Phase 3（一般公開）で他人に再配布する場合は再検討必須**。個人利用と再配布では規約リスクが桁違い
- **確実に取得してよいもの**: 自分で登録したソースのRSS、PR TIMESのプレスリリース（配信目的の媒体）、robots.txtで許可された公開ページ。
- **取得しないもの**: ログイン必須領域（FAMILY CLUB）、X/Instagram（下記Q4）、robots.txt拒否ページ。

## 3. 取得手段の使い分け（Q3）

| 手段 | 使う対象 | 備考 |
|---|---|---|
| **RSS** | PR TIMES等、提供があるソースのみ | 最も安全・軽量。ただし今回の対象サイトの多くはRSS非提供⚠️ |
| **公開API** | ほぼ存在しない | タワレコ・百貨店・STARTOにイベント公開APIはない（実装時に再確認⚠️） |
| **HTML取得＋抽出** | 公式巡回層の主力 | 一覧ページを取得→前回スナップショットとハッシュ比較→**差分がある時だけ**LLMで構造化抽出（Claude Haiku 4.5、後述） |
| **検索API** | 発見層の主力 | Brave Search API（無料枠 月2,000クエリ）等。「King & Prince POP-UP」「キンプリ イベント 大阪」等のクエリセットを日次実行し、未知URLを候補化 |

抽出の実装: まずCSSセレクタ等の決め打ちパーサを書き、**壊れた時・新規ソース追加時だけLLM抽出にフォールバック**するとコストと安定性のバランスが良い。LLM抽出はJSONスキーマ強制（structured outputs）で `イベント名/会場/期間/入場方法/主催者` を返させる。

## 4. 各手段の規約・技術上の制約（Q4）

| 制約 | 内容 | 対応 |
|---|---|---|
| X (Twitter) | 無料APIは検索不可・スクレイピングは規約違反 | **監視しない**。タワレコイベント公式X等は「手動確認リンク集」としてUI表示のみ |
| Instagram | Graph APIは自アカウントのみ | 同上 |
| ログイン必須領域 | FAMILY CLUB等。自動取得は会員規約違反 | 手動確認リスト化 |
| JSレンダリングサイト | fetchだけではHTMLに中身が無いサイトがある | Workersなら Browser Rendering API（Workers Paid $5/月で利用可）で対応可。まずは静的HTMLで取れるソースから始め、取れないソースは検索層でカバー |
| CORS | ブラウザから他サイト取得不可 | 収集はすべてサーバー側（Workers/Actions）で実行 |
| robots.txt | Disallowページは取得しない | fetcher組み込み（Q2） |
| レート・負荷 | 相手サイトへの配慮 | 低頻度・1接続・条件付きGET（ETag/Last-Modified）を使用 |
| 検索APIの地域性 | 日本語ローカル情報の網羅性はAPIによって差がある | Brave/Tavily/Google Programmable Search を実装時に比較。1本に依存しない設計（searchProviderを差し替え可能に） |

## 5. 重複統合（Q5）と event identity（収集段階の誤認防止）

**identity_key = norm(イベント名) + venue_id + 開始日 + norm(主催者)**

```
norm(): 全角→半角、大文字→小文字、スペース・記号除去、
        表記揺れ辞書適用（キンプリ→king&prince 等。oshi_keywordsを流用）
venue_id: venuesマスタで解決（「タワレコあべの」「タワーレコード あべのHoop店」→ 同一ID）
          未知の会場は新規venue登録（都道府県+施設名で仮ID）
```

統合ルール:
1. **identity_key 完全一致** → 同一イベント。event_sources に出典を追加しフィールドをマージ（公式値優先、Q8の規則）
2. **名前類似（trigram類似度 > 0.8）かつ 会場一致 かつ 期間重複** → 自動統合**しない**。`duplicate_candidates` に積み、管理画面で人間が判断（またはClaudeに判定させ、判定理由を記録）
3. **同名・同ブランドでも会場か主催者が違えば別イベント** — 「心斎橋でDisneyイベント」と「あべのHoopのK&P×Disney」は venue_id が違うので**構造的に混ざらない**。これが要件18の収集段階への適用
4. 検索発見で主催者不明の場合は `organizer='(未確認)'` の**仮identity**とし、公式裏取り時に確定キーへ差し替え（旧キーは alias として保持し再発見時の重複を防ぐ）

## 6. 「公式情報」と「検索発見の未確認情報」の区別（Q6）

ドメイン許可リストで機械判定する:

| レベル | 定義 | 例 | 表示 |
|---|---|---|---|
| **L1 公式** | 主催者・出演者・会場の公式ドメイン | starto.jp, universal-music.co.jp, tower.jp, disney.co.jp, d-kintetsu.co.jp | 「公式確認済」 |
| **L2 準公式** | 主催者発信のプレスリリース | prtimes.jp（発信元企業が主催者の場合） | 「公式発表あり」 |
| **L3 未確認** | アグリゲータ・検索結果・まとめ | fashion-press.net, collabo-cafe.com, 検索ヒット | **【要確認】** |

- イベントの status: `discovered`（L3のみ）→ `verified`（L1/L2ソースが1件以上）→ `ended`
- discovered イベントは通知にも「【要確認】＋確認先リンク」を必ず付け、「開催中」と断定しない
- **裏取りの自動化**: discovered イベントが生まれたら、次回巡回時にそのイベント名で公式ソース群を対象に検索し、L1が見つかれば自動昇格。見つからないまま7日経過したら「裏取り失敗」として管理画面に出す

## 7. 新規イベントの自動追加（Q7）→ **可能**

- **案2（Workers+D1）**: 収集WorkerがD1へ `INSERT`。アプリはAPI経由で読むため即反映
- **案1（Pages+Actions）**: Actionsが `data/events.json` を更新してcommit→Pagesが再デプロイ→アプリが起動時にfetchしlocalStorageへマージ。反映まで数分＋コミット履歴が収集ログで埋まる欠点
- どちらの案でも新規は `discovered` で入る（人手を経ずに verified にはならない、L1ソース直取得の場合を除く）

## 8. 既存イベントの自動更新（Q8）→ **可能**

- identity_key で既存イベントを特定し、**フィールド単位**で更新
- 優先順位: `ユーザー手動編集（manual_overrideフラグ付き） > L1公式 > L2 > L3`。手動で直した値を収集が上書きしない
- 更新があったら `event_revisions` に旧値・新値・出典・日時を記録 → 「開催時間が変わった」「整理券制に変わった」を**通知イベント**として扱える
- ソース再取得に成功するたび `last_verified_at` を更新。ページが404になったら `source_lost` フラグ→管理画面に出す（終了の可能性）

## 9. 取得頻度の可変化（Q9）→ **可能（tick方式）**

cron自体は**1時間ごとに固定で起動**し、起動した「スケジューラ」が今回何を取るかを決める:

```
毎時tick:
  mode = 判定(user_schedulesと今日の関係)
    通常日        → 朝8時のtickのみフル巡回（実質1日1回）
    遠征前日      → 8時/13時/20時に巡回 + 20時に「明日の推し活プレビュー」通知
    遠征当日      → 7時にフル巡回+朝通知、以降2時間ごとに軽量巡回（対象地方のソースのみ）
  検索発見層 → 通常日は日1回。遠征前日・当日は対象都市クエリを追加
```

- cron定義は固定のまま頻度が変わるので、**スケジュール変更にデプロイ不要**
- GitHub Actionsでも同じtick方式は組めるが、起動遅延（数十分ズレることが常態）があり「遠征当日の朝7時」が9時になり得る。Workers Cronはほぼ定刻

## 10. GitHub Actions cron vs Cloudflare Workers Cron（Q10）

| 観点 | GitHub Actions | Cloudflare Workers Cron |
|---|---|---|
| 費用 | publicリポジトリは無料 | 無料枠で可（Cron Triggers はFreeプランで利用可） |
| **起動精度** | ×: 混雑時15〜60分遅延が常態。時刻厳守の通知に不向き | ◎: ほぼ定刻（分単位） |
| 最短間隔 | 5分（実際はもっと粗い） | 1分 |
| 実行時間 | ◎: 最大6時間。重い処理向き | △: CPU時間制限あり（Freeで短い）。**多ソース巡回は1tickで数ソースずつ処理する分割設計が必要** |
| データ保存 | git commit（履歴汚染・競合リスク） | ◎: D1に直接書き込み |
| 通知 | ×: Push配信サーバーになれない（Discord webhook/メールは可） | ◎: **Web Push配信サーバーになれる**（VAPID） |
| フロントAPI | ×: 静的ファイルのみ | ◎: 同じWorkerがAPIも担う |
| 秘密管理 | Secrets | Secrets（wrangler） |
| 得意分野 | 重いバッチ（例: Claude Code Actionに「今週の推しイベントを調査させる」月次ジョブ） | 軽量高頻度の巡回・API・通知 |

**結論: この用途はWorkers Cronが適する。** 収集（軽量fetch×多数回）・通知（定刻厳守）・API（マルチデバイス）の3要件すべてでWorkersが勝つ。Actionsは将来「Claudeによる深掘り調査ジョブ」用に併用の余地あり。

## 11. アーキテクチャ比較: 現状維持 vs Workers+D1

| 観点 | 案1: GitHub Pages + localStorage（＋Actions収集） | 案2: Cloudflare Workers + D1 |
|---|---|---|
| **費用** | ¥0 | **¥0で開始可**（Workers Free: 10万req/日、D1 Free: 5GBストレージ・読取500万行/日）。Browser Rendering や Queues が欲しくなったら Workers Paid **$5/月** |
| **実装難易度** | 低（既存踏襲）。ただし「Actions→JSONコミット→localStorageマージ」の整合性処理が実は面倒（端末編集との衝突解決） | 中。ただし**あづさはWorkers+D1経験あり**で未知構成ではない。wrangler+SQLで素直に書ける。認証は最初「シークレットURL＋トークン」で自分専用に簡略化 |
| **通知** | ×〜△: Web Push不可（Pagesは配信サーバーを持てない）。代替はActionsからDiscord/メールのみ。**⑥スマホ通知の要件を満たせない** | ◎: WorkersがWeb Push配信（PWAをホーム画面追加すればiPhoneでも受信可、iOS 16.4+）。補助チャネルとしてDiscord webhookも1行で追加可 |
| **自動収集** | △: 可能だがcommit方式が不格好＋起動遅延 | ◎: Cron→fetch→D1が自然。頻度可変（Q9）も素直 |
| **マルチデバイス** | ×: 端末ごとに分断。JSON手動export/importのみ | ◎: D1が単一の真実。スマホ・PCどちらもAPI経由で同じデータ。将来のマルチユーザー化（Phase 3）もD1のuser_idカラムで自然に拡張 |
| データ喪失リスク | 高（ブラウザのサイトデータ削除で消える） | 低（D1＋定期エクスポート） |
| 既存資産の再利用 | — | **フロント（oshi-radar.html/CSS/logic.js）はほぼ全部使い回せる**。store.js の中身をfetch APIに差し替えるだけ（Phase 1でstoreのインターフェースを固定済み）。localStorageはオフラインキャッシュに降格して残す |

**推奨: 案2（Workers + D1）。** 最終形①〜⑥のうち①（自動発見）②（公式確認）⑥（スマホ通知）は案1では実質達成できない。③④⑤はPhase 1のlogic.jsをWorkers側に移植して使う。

```

```

## 12. パイプライン全体（最終形①〜⑥に対応）

```
① 発見     Cron tick → 公式巡回(差分検知) + 検索API
              ↓ 抽出（決め打ちパーサ / 壊れたらClaude Haiku 4.5でJSON抽出）
    identity照合（norm名×venue×開始日×主催者）→ 新規INSERT or 既存マージ or 重複候補
② 確認     ソースレベル判定 L1/L2→verified、L3→discovered【要確認】＋自動裏取りジョブ
③ 照合     user_schedules × イベント（既存logic.jsのスコア100点＋エリア拡張検索を移植）
④ 発火     見逃し防止条件A〜D or スコア80+ or 新発見が予定都市 → notification生成
⑤ 計算     「行けるか判定」エンジン（Phase 1実装済みをそのまま利用）で◎○△×とタイムライン
⑥ 通知     Web Push（PWA）+（任意でDiscord）。通知本文に判定結果まで含める:
            「9/8 大阪遠征日: K&P×Disney POP-UP＠あべのHoop、心斎橋から20分、△16:00発なら行ける」
```
